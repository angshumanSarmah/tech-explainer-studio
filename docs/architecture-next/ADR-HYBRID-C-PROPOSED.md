# ADR-020 — Hybrid C AI-directed media production

**Status: ACCEPTED by explicit user approval, 2026-11-12 (Asia/Kolkata).** Recorded in the [existing ADR register](../15-adrs.md#adr-020--hybrid-c-directed-media-production). Initially registered as PROPOSED earlier on the same date after checking available IDs. Filename retained for stable references. This is a forward-only architectural extension; accepted ADR-019, completed phases and legacy contracts remain preserved. Acceptance does not assert implementation or authorize starting a phase.

Read the [actual repository reconciliation](HYBRID_C_INTEGRATION_REVIEW_2026-11-12.md) with this decision: 11C engineering is accepted; media reservations/receipts, portable Kit ZIP and clip authoring/render support are missing. These are nonblocking implementation dependencies, not unresolved architectural conflicts. Existing services remain the integration owners. The user explicitly retained **Phase 09 private-only publication** and all existing release safeguards; older “unlisted” wording is not authoritative. No implementation or paid API authorization follows from architectural acceptance.

## Context and goal

The accepted Phase 11C design deterministically renders bounded, validated VideoScript 1.2.0 from an actual executable catalog. Manually authored examples proved engineering reuse but were visually limited. Users want open-ended technology explainers without a developer or Codex designing each video. An AI must select useful visual representations from approved evidence and may need **new per-topic images and short clips**; a finite pre-made icon library alone is insufficient. The application should remain achievable, testable, secure and low cost.

## Accepted decision

1. Adopt **Hybrid C**: an LLM Creative Director chooses narration, scene representations, intended animation, asset requirements and (where enabled) the appropriate production method. The Node.js application remains the **deterministic workflow authority** and executes only typed, supported and authorized operations.
2. Supported media strategies are: (A) exact declarative technical animations from current registered primitives; (B) approved images, layered imagery, manually imported media or provider-generated images; and (C) **optional** provider-generated video clips. Actual capability is discovered from implemented provider/render contracts, not assumed.
3. Continue **one** canonical, strictly versioned VideoScript authoring family, **one** compiled visual plan, **one** measured 24kHz/30fps timeline and **one** Remotion/FFmpeg Producer. No independent clip timeline or implicit subtraction of frames/audio for transitions. Do not widen 1.2.0 silently; if clip embedding requires authoring fields, propose an additive new VideoScript version and prove legacy pixels/validation unchanged.
4. Proposed **asset requirements / production intent** belong in the existing job/Director planning layer (or minimal separately versioned typed contract only if audit proves necessary), NOT as dangling asset IDs inside a render-ready VideoScript. Final scripts reference real immutable validated asset IDs after resource resolution. Production Plan/Asset Manifest are conceptual concerns; do not instantiate duplicate stores or schemas when existing types suffice.
5. Support **independent provider/model configuration for supported production stages** (Director, images, clips, narration), with explicit local/manual workflows. Reuse the existing Phase 06 `LLMProvider` for Director adapters; Content and Visual Director may initially share one provider/model. Media adapters follow established project patterns without a duplicate Director abstraction. An unavailable provider is a **disabled capability**, not a mock advertised as working; no automatic provider switch or capability claim is implied.
6. Export a portable **Director Kit** with current exact Zod-derived VideoScript JSON schema, executable visual catalog with limits, approved (optionally redacted) research context/claims, BrandProfile, verified examples, and versioned prompt instructions. External Claude, ChatGPT, Codex or other LLMs may generate strict declarative JSON without any integrated AI provider. The Studio must validate/import and render it through the same pipeline. Source export requires explicit data-sharing consent.
7. Media creation is **offered, not forced**. AI-generated video is OFF by default; image generation is independently configurable. A user can upload media or use current approved assets and fully local/programmatic rendering. The Director can propose a paid tool but cannot enable it or raise spending limits.
8. **Preview Before Spend:** show a storyboard and scene-level resource list with provider/model, estimated cost, total maximum, uncertainty, retry budget and accurate provenance status **before** paid media generation. Obtain operator approval bound to the immutable plan/provider/model/config/request digest. Allow selective approval/rejection; rejected media receives a supported alternative or remains blocked. A new plan or price ceiling invalidates approval. All paid Director calls require a separately pre-authorized planning budget; preview before spend for media does not imply free LLM planning.
9. Phase 07 must persist idempotent jobs/attempts, cost reservations, provider receipts when exposed, asset outputs/hashes and cache dependencies. Phase 08 owns factual, rights, draft and exact-artifact release gates. Generation does not authorize reuse rights or independently prove factual accuracy. Never silently send confidential source text to a remote model.
10. LLM outputs are **data only**. No runtime JS/TS/React/Three/HTML/SVG markup, arbitrary executable expressions, installed plugins, fetched media URLs in renderer, self-modifying tools, unbounded autonomous provider calls, or mandatory LangGraph/multi-agent orchestration.

## Delivery slices and ownership

Accepted incremental order: **11D → H1 → optional H2 → 12 → 09 → 10 → 13**; Phase 14 remains separately optional. Each gate requires separate implementation authorization and stops for review. Media provisioning runs through the same Node.js workflow authority before frozen assets enter the deterministic Producer; it adds no autonomous agent, renderer or narration timeline. Deferring H2 does not block ordinary videos or Phase 12; unsupported clip controls remain disabled.

- **11D (original + addendum):** real source-guided AI Director through existing CLI and Phase 06 provider; manual external JSON import; export Director Kit; bounded planner emits source-grounded script + typed *proposals* for optional required media. No image/video provider implementation in this phase. The first actual LLM run needs operator-configured credentials and budget.
- **H1:** imported/locally provided image assets and one image-provider integration, existing VisualAsset pipeline, common media preflight, immutable generation outputs and Preview Before Spend. Support local provider only if actually available and verified.
- **H2:** optional AI video clips, one video provider, media enable OFF by default, backend-enforced approval/budget and exact-duration muted clip composition through existing Producer. Do not require generated clips to render normal videos.
- **12:** UI on the same backend/CLI logic: provider model settings, source review, imports, toggles, proposals and approvals. Unimplemented providers are clearly disabled.
- **09/10/13:** approved generated-media provenance/exports and metrics, without bypassing the existing publication gates.

## Risks and protections

AI stills cannot reliably change internal parts without layered/cutout assets or structural animation; generated footage cannot guarantee technical correctness. Provider prices, maximum costs and outputs can change; expose estimates/unknowns, require known enforceable upper bounds before dispatch, and account for retry and concurrent work. Media generation may take time or fail; use existing persisted jobs and bounded retries. File import/generation requires content and size sniffing, sanitized/rasterized SVG, media metadata checks and file/path/URL security. Provider terms, consent, privacy and rights remain explicit review concerns.

## Alternatives considered

A only: easier but limited artistic variety and unfamiliar visuals. B only: visually flexible but harder to control exact technical state/labels/continuity and expense. Unrestricted runtime codegen: flexible but high security/reliability and maintenance risk. Whole new orchestrator/renderer: needless duplicated authority and cache/review drift. A staged hybrid delivers flexibility while maintaining one reproducible production pipeline.

## Acceptance record and implementation gate

The user explicitly accepted Hybrid C on 2026-11-12, including all nine requested capabilities and the incremental order above. Review of the actual integration report, ADR register and accepted ADR-019 found **no unresolved material architectural conflict preventing acceptance**. Existing image-only assets and 1.2.0 scripts cannot represent clips; a backward-compatible new authoring/asset version and deterministic placement policy still require review before H2 implementation. Planner persistence, Kit privacy/staleness handling, actual supported adapters and durable shared cost/attempt controls remain future work using the existing services.

Preserve original prompts, completed implementations, historical decisions, legacy readers/hashes and all factual/rights/playback/exact-artifact approval boundaries. General SVG sanitization/rasterization is not currently implemented; retain existing rejection of active/unsupported SVG unless a future validated extension is separately reviewed. Phase 09 is **private-only**. Architectural acceptance and engineering readiness do not approve any media, facts, rights or release and do not authorize phase implementation or paid APIs. **STOP; await a separate phase instruction.**
